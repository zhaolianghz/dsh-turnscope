# V0.1.3 — Drop Session-Bootstrap Context Nodes

## What the user reported

DSH records context-injection events as `context` conversation nodes
(`@deepseek-ai/dsh-client-runtime` `ContextMessageNode`). When a session
starts, the harness injects its initial instructions, catalog, and recall
state as a burst of context events — these arrive **before** the first user
prompt. The current renderer treats every context node as a turn activity
and attributes it to turn 1 (because `turnForSeq(seq)` falls back to "the
turn whose endSeq is `>=` this seq" and turn 1's endSeq covers everything
from the start of the session up to its first user prompt).

The user-visible symptom: every session shows one or two "Turn 1 / Turn 2"
cards whose activity list is a row of identical `Context` entries, and
whose detail page is similarly padded with empty `Context` rows. The agent
did nothing in those turns; the entries are session-startup noise the
renderer should not have promoted to a turn activity.

## Out of scope

- **Real session-start baseline snapshot.** The honest long-term fix is to
  capture a `recovery_before` for the first turn of every session, so the
  baseline-dirty state is recorded once and inherited from there. That is
  a schema-migration + session-start worktree write, not a renderer fix.
  Defer to a later release.
- **Marking the host-recorded terminal status more prominently** (the
  "主进程记录:已中断" chip). V0.1.2 already surfaces the host status as a
  second chip; making it more prominent is a separate UI polish.
- **Filtering mid-session context injections** that arrive between turns
  with no `turn` field. Those are real per-turn context events the user
  cares about; only the **pre-first-prompt** burst should be dropped.

## Goal

A `context` conversation node whose `seq` is **earlier than the first
`user` or `assistant` node's `seq`** in the same session is treated as a
session-startup event and is **not** included in any turn's activity list.

When the snapshot has no `user` / `assistant` nodes at all (the user
opened a session and never sent a message), the bootstrap rule falls back
to "keep everything" — there is no signal to distinguish bootstrap from
"the user is composing their first prompt", and dropping everything would
be worse than keeping the entries.

## Design

### Renderer (`src/client/turn-model.ts`)

Compute the bootstrap cutoff once, before the per-node grouping loop:

```ts
const firstRealSeq = snapshot.nodes.reduce<number | undefined>((min, node) => {
  if (node.kind === 'user' || node.kind === 'assistant') {
    return min === undefined ? node.seq : Math.min(min, node.seq)
  }
  return min
}, undefined)
```

A node is a bootstrap node when all of:

1. `node.kind === 'context'`.
2. `firstRealSeq !== undefined`.
3. `node.seq < firstRealSeq`.

Bootstrap nodes are skipped (`continue`) in the grouping loop, exactly
like the existing `if (turn === undefined ...) continue` skip. They
never enter any turn's `activities` array, never appear on the detail
page, and never inflate a turn's `activityCount`.

A non-context node with `seq < firstRealSeq` (e.g. a `steering` or
`compaction` that arrived during session bootstrap) is left in place —
the fix is specifically about context events the user has already
acknowledged in the chat log, not about filtering every pre-first-prompt
event. Steering and compaction are explicit user actions the user
already saw.

### Tests

`tests/client/turn-model.client.spec.ts` (the file already exists; the
new tests go alongside the existing ones):

1. `it('drops context nodes whose seq is before the first user/assistant node')` —
   build a snapshot with two `context` nodes at `seq = 1, 2`, then a
   `user` at `seq = 5`, then a `turn/end` at `seq = 10`. Assert turn 1
   has `activityCount === 1` (just the user message) and the activities
   list contains no `Context` entry.
2. `it('keeps context nodes that arrive after the first user/assistant node')` —
   context at `seq = 4`, user at `seq = 5`, assistant at `seq = 6`. Assert
   turn 1's activities include both context and user/assistant.
3. `it('keeps all context nodes when no user or assistant message exists yet')` —
   snapshot with only context nodes and no user/assistant; assert the
   activities are preserved (the renderer should not silently eat a
   pre-prompt context burst in a fresh session).

## Risk

- Pure renderer change. No wire-shape change, no `API_VERSION` bump, no
  DB migration, no worktree write, no LLM call.
- The filter is conservative: it only drops `context` nodes strictly
  before the first `user`/`assistant` seq. Mid-session context injections
  (with seq between two turns) are unaffected.
- The fallback when no `user`/`assistant` exists preserves current
  behaviour exactly — so a session that never received a user prompt
  still shows the entries, which is the right answer for that edge
  case.

## Success criteria

- A session whose pre-prompt activity is a burst of context events shows
  no `Context` rows on the turn 1 / turn 2 cards.
- The same session, after the first user message arrives, still shows
  all in-turn context events.
- A session with no user/assistant message at all is unchanged from
  V0.1.2.
- 595 tests + 3 new tests pass; typecheck clean; client bundle size
  change < 0.5 kB.
