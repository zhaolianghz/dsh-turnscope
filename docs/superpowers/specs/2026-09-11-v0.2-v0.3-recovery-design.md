# V0.2 Safe Rewind + V0.3 Fork & Retry —— 工程 spec

> **目的**:把 PRD §16 / §17 / FR-12–FR-15 的产品规则,翻译成"可被 writing-plans 直接分解"的工程方案。
> **基线**:V0.1 `feat-prd-subagent-development` 分支已落地(`pnpm test` 35 文件 / 496 用例全过),ARCHITECTURE.md §17–§23 / §28.5–§28.7 / §42 / §48 / §55 / §56 已给出高层工程方案,本 spec **收敛并补齐实现细节**,不重新设计。
> **范围**:V0.2 + V0.3 一份 spec,因为二者共享"字节级 reverse patch"这条底层。V0.3 中"DSH child session"分支尚需一次独立 spike(见 §10),spike 结论直接影响 V0.3 任务分解;**spike 失败时,V0.3 自动缩为"只生成 worktree,不创建 session"**。

## 2. 总体数据流

### 2.1 V0.2 Safe Rewind 流

```
UI: 用户点 [Preview Rewind]
        ↓
client RPC: previewRewind({turnId, evaluationId})
        ↓
host: 重新 observe(POST + CURRENT),重算 Safety
        ↓
        ├─ verdict != SAFE → 返回 SafetyVerdict,UI 关闭 Preview,提示 Fork
        └─ verdict == SAFE
                ↓
host: RecoveryPlanner.plan(turn, changeSet, post, current)
                ↓
host: RecoveryRunner.dryRun(plan) // 在 .turnscope/dryrun/<planId>/ 跑
                ↓
        ├─ dry-run 失败 → 返回 RECOVERY_STALE / plan 标 cancelled
        └─ dry-run 成功
                ↓
host: 落 recovery_plans(status=previewed),返回 planId + stateHash + operations
                ↓
UI: 显示逆向 diff / affected files / "expected after",要求 Confirm
        ↓
client RPC: applyRewind({planId, expectedStateHash})
        ↓
host: 再次校验 stateHash —— 不匹配返回 RECOVERY_STALE
        ↓
host: RecoveryRunner.apply(plan) // 写 recovery_before → temp → verify → atomic rename → recovery_after
        ↓
        ├─ 成功 → 落 journal + plan.status=completed,返回 RecoveryResult
        └─ 中途失败 → 落 journal[failed],尝试 journal + recovery_before 回滚;回滚失败返回可执行的 inspect 指引
        ↓
UI: 显示 RecoveryResult,Refresh Verdict
```

### 2.2 V0.3 Fork & Retry 流

```
UI: 用户点 [Fork & Retry]
        ↓
client RPC: createFork({turnId, checkpointId?})
        ↓
host: ForkEngine.create(input)
        ↓
  step 1: 解析 source checkpoint (prefferedId = turn.preCheckpointId || turnId)
  step 2: git worktree add <managedRoot>/worktrees/<forkId> <baseHead>
  step 3: 在新 worktree 内 apply checkpoint_paths 的 before-blob(脏基线 / 历史 turn 状态)
  step 4: 验证所有 blob hash,失败 → git worktree remove --force,落 forks.status=failed
  step 5: 创建 DSH child session (走 SessionForkPort,见 §6)
  step 6: 预填 Retry Context,不调用模型,等用户改 Prompt
        ↓
host: 落 forks 行(status=ready),返回 {forkId, worktreePath, childSessionId?, retryContext}
        ↓
UI: 跳转 / 显示 [Open Fork] 按钮 + Retry Context 编辑器
        ↓
用户在 child session 跑 N 个 turn(归 Turnscope 自己的 session_id,做 lineage)
        ↓
UI: 点 [Compare] → compareTurns({leftTurnId, rightTurnId})
        ↓
host: CompareEngine.compare(left, right) → TurnComparison(纯事实)
        ↓
UI: 显示对照表,不输出"哪个更好"
```

### 4.2 新增类型(在 `host/recovery/types.ts`)

```ts
type RecoveryFileOperation =
  | { kind: 'restore'; path: string; expectedCurrentHash: string; targetBlobRef: string }
  | { kind: 'delete_created_file'; path: string; expectedCurrentHash: string }
  | { kind: 'recreate_deleted_file'; path: string; targetBlobRef: string }
  | { kind: 'noop'; path: string; reason: 'unchanged' | 'baseline_only' | 'drift_preserved' }

interface RecoveryPlan {
  id: string                                    // turnId + ':plan:' + seq
  turnId: string
  verdict: SafetyVerdict
  evaluationId: string                           // 绑定到 SafetyVerdict.evaluatedAt + hash,防 stale
  stateHash: string                              // 工作区快照指纹(详见 §5.4)

  beforeCheckpointId: string
  status: 'planned' | 'previewed' | 'applying' | 'completed' | 'failed' | 'cancelled'
  createdAt: number
  expiresAt: number                              // stateHash 过期时间(默认 60s,见 §5.4)
}

type RecoveryJournalState =
  | 'prepared' | 'applied' | 'verified' | 'rolled_back' | 'failed'

interface RecoveryJournalEntry {
  planId: string
  seq: number                                    // 单调递增,Apply 中断时按 seq 续
  operation: RecoveryFileOperation
  state: RecoveryJournalState
  occurredAt: number
  error?: { code: TurnscopeErrorCode; message: string }
}

interface RecoveryResult {
  planId: string
  status: 'completed' | 'failed' | 'rolled_back'
  afterCheckpointId: string | null              // recovery_after 的 id,失败时 null
  journal: RecoveryJournalEntry[]
  failureReason?: string                         // 仅当 failed / rolled_back
}
```

## 5. V0.2 关键设计决策

### 5.1 决策 1:Recovery Plan 由纯函数生成,不读工作区

**理由**:ARCH §6.2「Safety 纯函数优先」延伸到 Recovery——plan 必须 deterministic、可 replay、可测试。生成 plan 的输入是已存储的 `TurnChangeSet` + `ObservedCheckpoint`(`PRE` + `POST` + `CURRENT`),Planner 不调 git,不读文件。

`host/recovery/planner.ts::plan(turn, changeSet, pre, post, current): RecoveryPlan` 是纯函数。`Runner.dryRun` / `Runner.apply` 是 side-effect 层,Planner 测试 = 单测 + property test(planner 给定输入 → operations[] 满足 §6.4 不变量)。

### 5.2 决策 2:Reverse patch 走"从 checkpoint blob 重新 derive unified diff",不持久化 diff 字节

**理由**:V0.1 已经为 relevant path 存了 `blobRef`(RECOVERY_BLOB,raw-bytes),planner 用 `before = storage.readBlob(change.beforeBlobRef)`、`after = storage.readBlob(change.afterBlobRef)` 重新 derive unified diff(沿用 V0.1 已有的 Myers `O(ND)` 引擎 in `host/diff/unified.ts`)。

为什么不预生成 diff 字节?一是 §44.2「lazy diff」原则:用户点 [Preview] 时再算;二是同一份 before/after 字节被多个 plan 引用时,持久化会重复。

### 5.3 决策 3:Dry-run 在受管 temp dir,**不**用 git worktree

**理由**:worktree 创建昂贵(整目录 git 元数据 + checkout),而 dry-run 只需"在隔离空间应用、验证 hash、不改原工作区"。用 `$DSH_HOME/turnscope/dryrun/<planId>/` 作为临时目录,git **完全不参与** dry-run:Planner 给出 operations,Runner 拷贝 before blob 到临时位置,模拟 apply,跑 verify hash,完事 `rm -rf`。

唯一例外:`recreate_deleted_file` 这种"原工作区当前没该文件"的,需要先 `git cat-file -p <blob>` 拿到字节 → 临时目录 → 比 hash。这个 cat-file 在 V0.1 ALLOWED_SUBCOMMANDS 里。

### 5.4 决策 4:`stateHash` = `sha256(workspaceId + HEAD OID + branch + worktree hash + relevantPathHashes)`

**理由**:Preview → Confirm 之间通常用户会去看 diff,耗时 < 60s。这段时间里工作区可能已经动了(用户在 DSH 别的面板手动改文件、跑命令)。`stateHash` 在 Preview 时算,Apply 时重算,**不一致直接拒绝**(`RECOVERY_STALE`)。

过期机制:Plan 带 `expiresAt`(默认 Preview 后 60s,configurable)。Client 在 Preview 后 60s 内不点 Apply,plan 自动标 `cancelled`,下次点 [Preview] 重算。

**hash 不含**:`.turnscope/` 内部目录、对象存储、未跟踪文件全表(否则每次自检就 invalidate)。

### 5.5 决策 5:Apply 顺序 = 「先写 recovery_before → 再 apply temp → atomic rename → 写 recovery_after」,每步落 journal

```
recovery_before checkpoint (phase=recovery_before)
        ↓
[FOR EACH op IN plan.operations]:
    write temp: <managedRoot>/apply/<planId>/<seq>/<basename>
    validate: temp sha256 == op.expectedCurrentHash(对 restore) / targetBlob sha256(对其他)
        ↓
    rename temp → final path(atomic rename,fsync parent dir)
    journal entry: {seq, op, state: 'verified', occurredAt}
        ↓
recovery_after checkpoint (phase=recovery_after)
        ↓
plan.status = completed
```

每一步前都校验 stateHash(中途用户改工作区 → `RECOVERY_STALE`)。中途**任一 op 失败**:

1. 已 verified 的 op 全部 rollback(用 recovery_before 字节 + journal 顺序逆操作)
2. 落 journal[failed]
3. plan.status = `failed` 或 `rolled_back`(看 rollback 是否成功)
4. 返回可执行 inspect 指引(用户能在哪个文件、哪个 hash、怎么用 `git checkout -- <path>` 手工还原)

### 5.6 决策 6:`RecoveryPlan.id` 用 `turnId + ':plan:' + ordinal`,按 turn 隔离

**理由**:同一 turn 可以多次 Preview(每次 stateHash 不同),`ordinal` = 该 turn 下递增。V0.1 `turnIdFor()` 已确定 turn id 格式,沿用。

### 5.7 决策 7:`applyRewind` 是写工作区的**唯一**入口

**理由**:架构守卫需要可静态检查"src/ 内不得有 `git reset --hard` / `git checkout -- .`" → V0.1 已实现。V0.2 的 Apply 路径走 `node:fs.rename` + `fsync`,**完全不经 git**。Recovery blob 的写入**也只能**走 Planner 决定的位置,Runner 不会主动扫描目录。

例外:`recreate_deleted_file` 用 `git cat-file -p <blob>` 拿字节,**只读**(`cat-file` 已在 ALLOWED_SUBCOMMANDS)。**永不**调 `git checkout` / `git reset` / `git apply` / `git read-tree`。

### 5.8 决策 8:架构守卫新增 4 条(V0.2 范围)

```
1. `src/host/recovery/` 不得 import `node:child_process`
2. `src/host/recovery/` 不得有 `'reset'` / `'checkout'` / `'--hard'` 字符串(除 import path 与注释外)
3. `src/host/fork/` 调用 `node:child_process` 只允许 `git worktree add|remove|list` / `git cat-file -p`
4. `src/host/fork/` 不得包含 `--force` 在 worktree remove 之外
```

实现:扩 `tests/host/architecture/guards.spec.ts`,新增 fixtures。

## 6. V0.3 关键设计决策

### 6.1 决策 9:Fork 用 git worktree(`git worktree add`),不走任何自造实现

**理由**:worktree 是 Git 原生的"同一仓库多 checkout",DSH 第一方、其他插件都在用。Turnscope 只是消费者。Runner 加白名单:`worktree add` / `worktree remove` / `worktree list` / `cat-file -p`,**禁** `--force`(必须先 clean 才允许 remove)、**禁** `--detach` 之外的所有路径模式(强制基于已有分支)。

### 6.2 决策 10:worktree 受管 root = `$DSH_HOME/turnscope/worktrees/<forkId>/`,带 `.turnscope-managed` 标记

**理由**:见 ARCH §56「清理不能触及非插件创建的 Worktree」。每个 worktree 创建后立即在根下 touch 一个空文件 `.turnscope-managed`,内容 = forkId。Cleanup 必须先验证:

1. 路径前缀 = 受管 root
2. `.turnscope-managed` 文件存在且 forkId 匹配
3. worktree 状态 clean(`git status --porcelain` 无输出,或经用户同意强清)
4. 无 active recovery 引用此 checkpoint

任一不满足 → 拒绝并 `FORK_NOT_MANAGED`。

### 6.3 决策 11:`SessionForkPort` 是 Port,实现 = Adapter(§10 spike 决定形态)

**理由**:ARCH §21 已经定义 `interface SessionForkPort { createSession({cwd, parentSessionId, parentTurnId, metadata}) }`。DSH 暴露什么 API 决定 Adapter 怎么写。

**spike 三种可能结果**:

| 结果 | Adapter 形态 | 影响 |
|---|---|---|
| (a) DSH 允许第三方调 session 创建 | Adapter 直接调,lineage 写到 DSH session metadata | V0.3 完整 F-04 |
| (b) DSH 不允许,但允许"插件启动一个 DSH 子进程" + 自管 session 元数据 | Adapter 走 `child_process.spawn('dsh', ['session', 'new', ...])`,lineage 只在 Turnscope SQLite | V0.3 完整 F-04(但 child session 不在 DSH 原生侧栏) |
| (c) DSH 完全不暴露 | Adapter 返回 `childSessionId: undefined`,worktree 创建后只返回 `{forkId, worktreePath, retryContext}`,UI 提示"用 DSH 命令面板手动开新会话,粘贴 Retry Context" | F-04 缩为**可选**,其他 V0.3 能力不变 |

**spec 接受三种结果**;V0.3 实施计划前必须有 spike 结论。

### 6.4 决策 12:Fork baseline 重建 = 「先 worktree,然后 apply checkpoint material」

**理由**:ARCH §20.3。`git worktree add <path> <baseHead>` 给我们一个干净的 checkout。然后 Runner 读 source checkpoint 的 `checkpoint_paths` 行,把 `before` blob 写到 worktree 对应路径。脏基线 / 历史 turn 状态二选一:

- `pre_checkpoint` + `current = pre` 的工作区 = Turn 起始时用户已脏的状态
- `post_checkpoint` + `current = post` 的工作区 = Turn 刚结束时的状态

默认 = `post`(Fork Retry 通常想"从 Turn 结束后那一刻重新跑")。config 可改。

### 6.5 决策 13:Retry Context 不复制大量 Trace

**理由**:ARCH §22「不要把大量原始 Trace 自动塞进 Prompt」。预填 5 段:

```
## Retry from Turn #N

Original task:
<turn.summary>

Previous failure:
<narrow factual summary from commands/tests>

Relevant files:
<change.path 去重,前 20 个>

What you can see in Turnscope:
<一行:打开面板看完整 Evidence>

Please retry with a different approach.
```

由 Turnscope 自动生成,**用户必改**(UI 不允许直接提交未改的 prompt)。

### 6.6 决策 14:Compare 不做语义比较

**理由**:FR-15 / ARCH §23 末尾明确"不输出 retry is objectively better"。TurnComparison 只列字段,不输出 verdict。UI 不给星星 / 分数 / 推荐,只给"left 在 X 文件上 Y 命令是 N,right 是 M"这种事实。

## 7. Host API 扩展

### 7.1 在 `shared/contracts/api.ts` 新增(API_VERSION 2 → 3)

API_VERSION 升级是因为新增方法 + 现有 TurnComparison 形状影响 client。v1 client 对 v3 host 在 listTurns/getTurnDetail/getDiff/evaluateSafety 仍兼容(只多方法);反过来 v3 client 调 v2 host 时,client 的 unwrap 在缺少 endpoint 时返回 `unusable`,不抛。

```ts
export const API_VERSION = 3

interface PreviewRewindRequest {
  turnId: string
}

interface PreviewRewindData {
  plan: RecoveryPlan              // status=previewed
  reverseDiffs: Record<string, FileDiff>   // path → diff,只算用户点过的路径 / 一次全算(见下)
  expiresAt: number
}

interface ApplyRewindRequest {
  planId: string
  expectedStateHash: string
}

interface ApplyRewindData {
  result: RecoveryResult
}

interface CreateForkRequest {
  turnId: string
  preferredCheckpointPhase?: 'pre' | 'post'    // 默认 'post'
}

interface CreateForkData {
  fork: ForkRecord
  retryContext: RetryContext
  childSessionAvailable: boolean                 // §6.3 spike (c) 情形时为 false
}

interface ListForksRequest { workspaceId: string }
interface ListForksData { forks: readonly ForkRecord[] }

interface CleanupForkRequest { forkId: string; force?: boolean }
interface CleanupForkData { fork: ForkRecord }   // status=removed 或 failed

interface CompareForkTurnRequest { leftTurnId: string; rightTurnId: string }
interface CompareForkTurnData { comparison: TurnComparison }
```

`reverseDiffs` 一次性给:**不**走按需(`getDiff` 是 V0.1 已有 endpoint,这里复用)。理由:Preview 是"我要看清要干什么"的场景,全算避免来回;字节上限由 plan 中 operations 数量自然限制(典型 < 50 个文件)。

### 7.2 在 `host/api/service.ts` mount 新方法

V0.1 已有 `mountTurnscopeRemoteWhenReady(ctx, ...)`。新增 6 个 method 描述(`previewRewind` / `applyRewind` / `createFork` / `listForks` / `cleanupFork` / `compareForkTurn`),全部走同一 Remote 通道。

descriptor 用 V0.1 spike 已验证的"显式 contribution"风格(无装饰器,直接 `TypertRemoteService` 子类 + 手写 descriptors)。

### 7.3 Client 接入

V0.1 client 的 `host-api.ts` 是 typed wrapper。新增 6 个对应函数(`previewRewind` / `applyRewind` / `createFork` / `listForks` / `cleanupFork` / `compareForkTurn`),全部走 `readReply<T>`(V0.1 的版本信封已就位)。

## 10. 前置 spike:V0.3 DSH child session 可行性

### 10.1 必须做(V0.3 实施计划启动前)

`docs/spikes/2026-09-11-dsh-child-session.md`(仿 V0.1 的 `2026-09-11-third-party-remote.md`):

- 装一个最小第三方插件:

  - client: 手写 remote-client 等价描述
- 测三件事:
  1. **能否调任何 session 创建 API**(直接调用或经 plugin surface)
  2. **能否在 metadata 里挂 parent_session_id + parent_turn_id**(让 DSH 自己渲染或让我们自己 join)
  3. **能否让 DSH 在 UI 侧栏显示"this is a child of session X"**(可视化 lineage)
- 实测命令:`dsh plugin --profile smoke add <repo>` + `dsh --profile smoke --dump-config` + 真实 boot + curl `/api/<namespace>/tryCreateSession`

### 10.2 三种结论的应对

- **(a) 完整可行** → F-04 完整,V0.3 不缩
- **(b) 部分可行**(能创建不能挂 metadata 或不能显示) → Adapter 用 DSH API 创建 + lineage 写 Turnscope 自己的 SQLite,UI 在 Turnscope 内自渲染
- **(c) 完全不可行** → §6.3 决策 11 缩 F-04:`childSessionAvailable: false`,UI 提示"用 DSH 命令面板手动开新会话"

### 10.3 spike 失败的代价

**不阻塞 V0.2**——V0.2 与 V0.3 的 spec 是独立的,V0.2 可先实施,V0.3 等 spike 结论。spec 接受这一时序。

## 11. 风险与降级

| 风险 | 触发 | 降级 |
|---|---|---|
| Planner 在大 turn(> 100 文件)性能差 | benchmarks > 1s | Planner 异步生成,Preview UI 显示 "Generating plan…" 进度条 |
| Apply 写入时磁盘满 | ENOSPC | 落 journal[failed],rollback 已 verified 部分,返回"磁盘满 + recovery_before 在 <path>" |
| worktree 创建后立即被外部 remove | forks.status=ready 但路径消失 | cleanup 显示 NOT_MANAGED,无需 panic |
| DSH session API 变化 | 同 §60 风险 1 | SessionForkPort 隔离 + Adapter 单点修改 |
| 用户在 Apply 中途反复点 Apply | 网络重试 | planId 唯一 + status 守卫,二次 Apply 返回 `RECOVERY_BLOCKED` |
| recovery blob 原字节含 secret | 同 §60 风险 | 沿用 V0.1 `0o600` + 受管 root + 无网络守卫,README 明示 |
| 跨平台(windows) | worktree path 行为差异 | V0.2/V0.3 同步声明 macOS/Linux,windows = best-effort(同 V0.1 旧计划 §12 风险表最后一行) |
