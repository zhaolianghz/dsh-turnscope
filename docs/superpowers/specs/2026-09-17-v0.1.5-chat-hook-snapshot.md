# V0.1.5 — Use `useChat` Hook for Chat Data (Fix the Wrong Snapshot Source)

## Problem (root cause, finally verified)

V0.1 → V0.1.4 was built against an outdated mental model of DSH runtime's
conversation data plumbing. The plugin reads chat data through `useSession` and
selects fields like `snapshot.nodes`, `snapshot.turnTimings`, `snapshot.turnEnds`,
`snapshot.chat.legacy.nodes`. **None of these fields exist on the actual snapshot
DSH 0.1.6-alpha.1 gives to the `'conversation.view'` slot.**

### Evidence (live from a real DSH profile + DSH session `session-1b67cfff-…`)

The debug log in V0.1.4 (built from the user's reported console) prints the full
key set of every snapshot `useSession` returns:

```
[V0.1.4 DEBUG] snapshot keys:
  sessionId, queue, pendingSubmissions, running, subagent, removed,
  openState, openError, hasMore, loadingOlder, promptError, blank,
  lastAgentError, promptAttempted, awaitingFirstTurn
  | chat keys: undef | legacy keys: undef
```

The snapshot has exactly **15 fields**, all session-lifecycle / interaction-state
metadata. None of `chat`, `nodes`, `turnTimings`, `turnEnds`, `legacy`, `views`,
`partial`, `runningCalls`, `composerPhase`, `promptError` (we do see
`promptError` here actually — that's fine), `pending`, or `subagent.address` is
exposed through `useSession`.

### Why V0.1.x typecheck still passed

The turnscope worktree installs `@deepseek-ai/dsh-client-runtime@0.1.1-rc.2` as a
dev dependency — that older package re-exports a `ConversationSnapshot` type
with the expected `chat.legacy.{nodes, turnTimings, turnEnds}` shape. TypeScript
is happy because the **type** exists in the local node_modules.

But the **runtime** is served from `@deepseek-ai/dsh@0.1.6-alpha.1`'s bundled
client (in `/Users/skyzhao/.nvm/versions/node/v22.23.1/lib/node_modules/@deepseek-ai/dsh/`).
That build serves `SessionSnapshot` (15 fields) to `useSession` and provides a
**separate `useChat` hook** that returns a `ChatSnapshot` containing the actual
chat data. There is no `@deepseek-ai/dsh-client-runtime` package shipped by
0.1.6-alpha.1 at all — the runtime was inlined / refactored between rc.2 and
alpha.1.

### What V0.1.x has been doing for the entire V0.1 line

Every call of the form

```ts
useSession(s => deriveTurnModels(s))
```

passes the 15-field `SessionSnapshot` into `deriveTurnModels`, which assumes
`ConversationSnapshot` (with `nodes` / `turnTimings` / `turnEnds`). The select
chain returned either:

* `undefined` (when `deriveTurnModels` short-circuited on the V0.1.4 null-guard),
  — making `turns` stay empty and the view show the empty-state card; or
* threw on the pre-V0.1.4 versions (V0.1.3 deployment crashed with
  `Cannot read properties of undefined (reading 'filter')` for the same
  reason).

V0.1.x has never once shown a real turn timeline on real DSH sessions. The
empty state was the only thing ever observed because the data source was
always wrong. **This is the real "活动 0" / "此会话还没有可显示的轮次"
defect — not a V0.1.3 regression.**

## Goal

Migrate the renderer (client) to read chat data from the `useChat` hook
(`ChatSnapshot`) instead of from `useSession`'s `ConversationSnapshot`. Keep
all renderer behavior intact (turn list, status / safety / activity / files,
recommended action, recovery section). Drop the V0.1.4 empty-state defensive
guards — they were workarounds for the wrong source, not the real fix.

Scope is renderer-only. Host side (`inspector`, `recovery`, `query`,
`storage`, `a2a/turnscope`) is untouched. RecoverySection already uses its own
remote-answers / useState flow and is not affected by this change.

## Non-goals

* No work on `SessionSnapshot`'s metadata fields. `openState` continues to
  come from `useSession`.
* No changes to the `'conversation.view'` slot registration order (still 20).
* No host API additions, no schema migration, no V0.2 recovery rewiring.
* No migration of the legacy `ConversationSnapshot` types in `tests/client/support.ts`
  — discarded with the source change.

## Design

### Source: `useChat` hook → `ChatSnapshot`

`@deepseek-ai/dsh-client-ui-conversation`'s runtime (served by DSH
0.1.6-alpha.1's `dsh-client-ui-chat`) declares `chat` as a session-scope hook
on every `'conversation.view'` slot:

```ts
// from dsh-client-ui-chat/lib/client.js (observed in DSH 0.1.6-alpha.1)
ctx.uiSession.provide({
  hooks: ['chat'],
  resolve: (binding) => ({ hooks: { chat: chatSource(binding) } })
})
```

`chatSource(binding)` returns:

```ts
{
  getSnapshot: () => ctx.uiConversation.binding(binding).target('chat').getSnapshot() ?? EMPTY_CHAT_SNAPSHOT,
  subscribe:  (listener) => target.subscribe(listener)
}
```

…i.e. the live `ChatSnapshotBuilder` output for the `'chat'` target, with
`EMPTY_CHAT_SNAPSHOT` (a `ChatSnapshot` with empty maps) as the absence
fallback.

Slot props type extension: `@deepseek-ai/dsh-client-ui-conversation`'s
`PropsRuntime<'conversation.view'>` resolves to `OwnerOf<K> & KeyPropsOf<K, …>
& SlotInjectFace<SlotInjectOf<K>> & SessionStandardProps & GlobalStandardProps`.
`SessionStandardProps` ships empty in `@deepseek-ai/dsh-client-ui-slots`;
`@deepseek-ai/dsh-client-ui-session` augments it with `useSession: SessionSnapshotSelector`,
`sessionId`, `useProjection`. **`useChat` is not declared in the augmentation,
because `chat` is provided as a slot inject hook (not a standard kit hook) by
`dsh-client-ui-chat`.**

We therefore type the slot component as receiving `useChat` via the standard
React render-prop shape: when DSH injects `{ hooks: { chat: chatSource } }`
into a `'conversation.view'` entry, the framework materializes it into the
component props as a `useChat` selector hook (matching DSH's own
`ApprovalCommand`, `ChatView`, `TurnTailNodeView` usage in the same
`dsh-client-ui-chat` package, e.g. `useChat((s) => s.order)` etc.).

### New renderer data flow

```ts
// TurnscopeView (ConversationViewProps)
function TurnscopeView(props: ConvViewProps) {
  const openState = props.useSession(s => s.openState);
  // ← single useChat selection: subscribe to the chat builder output.
  const chat = props.useChat();           // returns ChatSnapshot | undefined
  // fallback to EMPTY_CHAT_SNAPSHOT so callers see a stable shape and
  // subscribe identity is preserved across the very first frame.
  const safeChat = chat ?? EMPTY_CHAT_SNAPSHOT;
  // derive once per render, stable by ChatSnapshot identity.
  const turns = useMemo(() => deriveTurnModels(safeChat), [safeChat]);
  …
}
```

`deriveTurnModels` no longer reads from `useSession` — it consumes the
`ChatSnapshot` directly. It keeps the V0.1.3 first-real-seq bootstrap-context
filter (don't drop it as part of this fix; the spec for V0.1.3 still applies
because the same `ChatSnapshot.legacy.nodes` flow feeds into it).

### `deriveTurnModels(chat: ChatSnapshot): readonly TurnModel[]`

Input: `chat` is a `ChatSnapshot` (`@deepseek-ai/dsh-client-ui-conversation/client`).

Steps:

1. `const turns = chat.legacy.turnTimings` — `ReadonlyMap<number, { startTime; endTime? }>`.
   Empty map → return `[]` (no turns yet, "blank session" state).
2. Compute `firstRealSeq` over `chat.legacy.nodes`:
   `firstRealSeq = min(seq of nodes where kind === 'user' || 'assistant')`. If
   no real node exists, `firstRealSeq = Number.POSITIVE_INFINITY` so the
   filter never drops anything (preserves V0.1.3's no-real-prompt fallback).
3. Group `chat.legacy.nodes` by `turn` (skipping `kind: 'context'` with
   `seq < firstRealSeq` per V0.1.3).
4. For each `turn` in `turnTimings.entries()` (insertion-ordered Map iteration,
   which matches DSH's turn publication order):
   * `turnEnds.get(turn)` ⇒ end timestamp (or `undefined` while running).
   * `turnTimings.get(turn).endTime` ⇒ end timestamp (or `undefined`).
     Either source agrees; prefer `turnEnds` for status inference.
   * Group `legacyNodes` for this turn, drop context bootstrap per V0.1.3.
   * Derive activities, status, safety, file-changes etc. as today.
   * Build a `TurnModel`.

The `turnEnds` survived checks from V0.1.0 still apply: a turn whose
`turnEnds.get(turn) !== undefined` is `completed`; `turnTimings.get(turn).endTime`
absence ⇒ `running`; absence of `startTime` is impossible for a key present
in `turnTimings`.

### Type re-exports

`@deepseek-ai/dsh-client-ui-conversation/client` already exports `ChatSnapshot`,
`ConversationNode`, `ChatNode`, `ConversationNodeKind`, etc. (see
`node_modules/@deepseek-ai/dsh-client-ui-conversation/lib/types/client/index.d.ts`).
The turnscope client code imports them from there and stops importing from
`@deepseek-ai/dsh-client-runtime/client`.

### Risks / constraints

1. **`useChat` may be undefined on the very first render.** The slot framework
   mounts slot entries before the chat binding's hookContext is resolved, just
   like `useSession` is sometimes `undefined`. We accept `undefined` and
   substitute `EMPTY_CHAT_SNAPSHOT` (`chat.legacy.turnTimings.size === 0` ⇒
   the function returns `[]`). This is structurally identical to the V0.1.4
   empty-state handling, but at the correct location (data source rather
   than every readsite).

2. **`ChatSnapshot` identity is stable across the `chat` builder's
   `apply()` calls.** The builder returns a new `ChatSnapshot` only on real
   changes, so `useMemo([chat])` is correct (no recompute storm). Verified by
   DSH's own internal `useChat((s) => s.order)` selectors in
   `dsh-client-ui-chat/lib/client.js`.

3. **No host changes.** The remote answer `host` contract (queries, recovery)
   is independent of the chat view; we don't touch it. Existing host tests
   are unaffected.

4. **No recovery surface change.** `RecoverySection` reads from its own
   remote-answer keys (wired in V0.2). It does not consume
   `ConversationSnapshot` / `ChatSnapshot`.

5. **No V0.1.4 workarounds remain.** Once `useChat` is wired and `deriveTurnModels`
   reads from `ChatSnapshot`, the V0.1.4 `?? new Map()` / `?? []` defaults are
   no longer necessary (the source is `ChatSnapshot` directly, never
   `undefined` at that point — we substitute `EMPTY_CHAT_SNAPSHOT` once at the
   top of `TurnscopeView`).

6. **No API version bump.** `API_VERSION = 4` (since V0.1.1) stays at 4. The
   turnscope RPC contract (host-side) does not change. The renderer-side data
   flow is internal to the plugin.

### Out of scope

* Fork / retry V0.3 features.
* Anything that would also re-introduce the assumption that
  `useSession(s => s.chat.legacy.X)` is a valid read.

## Acceptance criteria

1. With DSH 0.1.6-alpha.1 active on the `web` profile and a real DSH session
   (e.g. `session-1b67cfff-74b7-4405-a708-37b5bd90c307`) loaded:
   * `TurnscopeView` renders a turn list with one entry per turn in the
     session's `turnTimings` map (not zero entries).
   * Status reflects the turn's actual `turnEnds` / `turnTimings.endTime`
     state (`completed` when both have an end, `running` otherwise).
   * Activity counts, file-change counts, and recommended action are populated
     from the host query (the same as V0.1.4's intended behavior).
2. With an empty DSH session (no turns yet), the empty-state card renders
   exactly as it did in V0.1.4.
3. `pnpm typecheck` clean.
4. `pnpm test` green, full test count growth is +N (or net equivalent) for
   the new `ChatSnapshot` fixtures; coverage of the previous snapshot-shape
   behavior is preserved (empty / single / multi-turn / bootstrap drop).
5. `pnpm build` clean; bundle sizes within ±2 kB of V0.1.4.
6. Release commit + tag `v0.1.5` annotated + pushed to `feat-prd-subagent-development`.
7. README changelog updated; "Status" block updated to V0.1.5.
